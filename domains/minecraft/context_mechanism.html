minecraft 域 · 长运行上下文管理机制

OpenKAGE/domains/minecraft — 一天一轮 ReAct，跨天靠记忆层，跨轮靠 consolidate
核心取向：压缩按「信息是否过期」分类，而不是按 token 数截断。 坐标 / 库存会过期 → 砍；「这一步干了什么、成没成」不过期 → 留。 计划中间态过期 → 砍；状态变更行（第 3 步：pending → success）不过期 → 留。 全局没有 token 预算、没有摘要式 compaction —— 只有三层按时间尺度分工的结构化取舍。

压缩生效了吗 —— 两个计数器

压缩只发生在发给 LLM 的消息里、不进日志。没有计数器就只能靠读 dump 才知道有没有生效， 而失效是静默的。故 builder 自带 n_trimmed（砍掉的旧观察份数）与 n_plan_trimmed（收敛的计划快照份数）， 每天随 ReAct 结束打进日志行（__init__.py:943-951）：

这两套本来就是分离的 —— 所以天内的上下文压缩 不会让夜反思少看到东西。这也是为什么压缩坚持「不改 history」的第二个理由： history 是 ReActAgent 的事实记录，就地裁剪等于篡改自己的轨迹，调试时看不出真相。

为什么记忆层必须常驻，而不能走 retrieve

「我的营地在哪」「昨天有什么没做完」—— 没有人会想到去查它。 向量检索天生答不了这类问题：query 是「我现在想干什么」，记忆是「我在哪、我做过什么」， 两者语义不匹配（这也是检索恒 0 命中的成因之一）。不常驻的后果是 Agent 每天醒来都是个新人：不知道在哪扎过营、箱子放哪、昨天计划挖矿但天黑没去。

层内容出口是否聚合进主脑
memory 专名：day_N、营地、矿洞、坐标 全量常驻注入（仅此一条） 永不 —— 只给明天的自己
experience 通名：归纳出的、可共享的结论 Agent 用 retrieve 按当下意图取 是 —— consolidate

两层各有各的通道，谁也不串到对方那边：聚合侧只读 experience （consolidate._dump_arm_graph 传 LAYER_EXPERIENCE）， 注入侧只出 memory。混成一块的后果是读的人分不清哪些明天还算数。 公共图谱（主脑）在白天只报 facet 条数让 Agent 自己判断值不值得查，不注入内容。

护栏：memory_dump_max_concepts = 40

撞顶按 ORDER BY updated_at DESC 丢最近未被活动过的，打 info 而非 warning —— 旧值 150 形同虚设（30 夜长跑实测记忆层 稳定在 47~78，从不触发）；40 低于实际规模，让滑动窗口真正工作、稳定淘汰最老的。 updated_at 由写图谱的工具回写维护（碰概念内容就推进），不是建后不动。

★ 排序刻意不按 slug：字典序会让 day_1 / day_10 / day_2 … 超过 9 天就乱，而且撞顶时丢掉的会是字典序靠后的地点概念 （east_mine / my_camp_1）—— 而 where 里的坐标恰恰是唯一跨天不失效的信息， 丢掉它等于丢掉护栏想保住的东西。

若把 STOP 当成新的一天，「第 2 天」其实会是同一个夜晚的后半段 —— 天号、计划、dump 文件全错位。 根因是 Agent 缺少「我要等」的正当表达，已补 waitUntil 原语并在 prompt 里写明 「没事做就 waitUntil、别停」；两者一起才治得住。 resume 时 daylight_note 按实际观察算、不写死—— day_over 只在步边界采到夜→昼时才置位，世界可能已天亮而那次跳变还没被采到， 写死「天还没亮」会与紧接着的【当前观察】自相矛盾。

5四条分离契约

两者为什么必须分开
压缩 ／ historyhistory 是 ReActAgent 的事实记录，就地裁剪等于篡改自己的轨迹，调试时看不出真相
夜反思 ／ ReAct history反思读 env 侧独立累积的 day_steps，与压缩无关 → 压缩不会让反思少看到东西
memory 层 ／ experience 层一个永不聚合只给明天的自己，一个必须聚合进主脑；混在一起读的人分不清哪些明天还算数
dump ／ 真实请求刻意不分开 —— 走同一个 build_messages 出口，故 dump 就等于发出去的上下文

6代价

这套比滑动窗口精确，代价是每一类返回值都要人工判一次时效性，而且这些判断散落在两侧、 靠约定维系。OBS_SEPARATOR 必须由 env 与 builder 两处保持一致， 就是这个代价最具体的形态 —— 改动任一侧的拼接格式，压缩会静默失效 （n_trimmed 恒为 0 是唯一可见征兆，这也正是那两个计数器存在的理由）。
